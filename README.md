# 素材生成

这个仓库是一条商品素材流水线。它把一份商品资料变成可以交给下游剪辑的分镜、静帧和短视频片段。仓库里是生产这些素材的规则、脚本和契约，不是成片平台，也不替代已有的剪辑系统。

一条可用素材要让人看懂三件事：眼前的具体麻烦、这件商品怎样插手、同一个麻烦被解决之后看得见的变化。功能靠画面演出来。问答、清单式测评、角标和水印都不进入画面。

## 一条素材怎么走完

顺序不能跳。后面的步骤只相信上一份已经落盘、并且哈希对得上的记录。

1. **商品资料。** `cases/<product_id>/case.json` 写明商品事实、已知功能和参考图位置。功能必须来自这份资料。推测出来的使用场景要标成创作假设，不能写成用户反馈或实测性能。
2. **整批分镜。** `create` 一次写出这一批镜头。每个镜头要能放进一条因果链：痛点、商品动作、对应结果。纯产品特写只占很少的名额，换个角度但没有新的购买信息，按重复处理。
3. **摘要。** `summarize` 把这一批压成一份摘要。摘要必须对应当前的分镜文件；分镜一改，摘要就失效，必须重做。
4. **审核与改提示词。** `review` 只根据摘要重写图像提示词，并给出整批是否通过。单镜返修走 `recreate` 或 `repair`，不把整批推倒重来。
5. **人工打分。** `score-template` 生成打分表，人填完后用 `score-submit` 提交。`jobs` 和 `video-jobs` 会检查这份表是否对应当前审核、当前分镜和当前商品。没有提交通过的表，不能出图、不能出视频任务。
6. **文本参考门。** `gate` 用本地模型对方案做文本判断，只给人工打分表提供参考列。这一关没过，或服务没起来，都不阻断后续任务。
7. **出图。** `jobs` 只生成打分表里选中的镜头。出图前要有单独的人工授权，并先记账再调用。默认没有授权就不会打到付费接口。
8. **看实际像素。** 出图之后必须有人，或有读图能力的程序，逐张看像素并写下看见了什么。提示词、文件名和模板不能代替这次观看。图、分镜、提示词或动作任一改变，原来的像素记录就作废。关键项没过，不能转视频。生成画面也不能当成真实性能的实验证据。
9. **视频。** 静帧已经存在，才写视频动作和时长（`motion`、`pace`）。`video-jobs` 准备任务，`video-submit` 在再次核对授权、图片和审核之后才提交。每批最多 10 条，每条不超过 10 秒。
10. **入库。** 下载回来的片段按审核状态放进 `material-library/<product_id>/`。下游剪辑只读 `approved/`。改状态时，视频、封面和旁路说明一起移动。

## 画面和数量

主验收标准是：观众能认出自己的具体麻烦，看懂商品怎样介入，再看到这个麻烦被解决。皱眉、泛泛的凌乱、人物微笑或一张漂亮桌子，都不能代替这个过程。

为了凑场景而引出这件商品解决不了的问题，整条镜头作废。功能链上的麻烦可以换到另一个地方、另一件物体，或拍出用完之后看得见的变化，但不能整批都是同一张桌子上的产品特写。

数量上限：

| 项目 | 上限 |
|---|---|
| 每个商品生成图 | 20 张，其中约 5 张留给返工 |
| 有效图 | 15 张 |
| 有效图的建议分配 | 痛点或后果 5、动作 4、结果 4、纯产品细节最多 2 |
| 完整人物 | 3 |
| 只有肢体入画 | 3 |
| 每批视频 | 10 条 |
| 每条视频 | 10 秒 |

15 张是规划上限，不是必须凑满的下限。素材少的时候，先把一条完整因果链做完。

画面里不能出现固定文字、制作说明、审阅状态，也不能把这些字挪到角落冒充没有字幕。来源和假设留在工程记录里。

## 目录

| 目录 | 里面是什么 |
|---|---|
| `cases/` | 商品资料、产品参考图和出镜人设。只留在运行机器上，不进入公开仓库 |
| `scripts/material-flow.py` | 日常入口。不要按文件名把脚本批量跑起来，不少命令会调用模型或提交任务 |
| `adapters/` | 各供应商的请求、门禁和素材桥接。自动剪辑侧的视频接口和官方视频接口互不导入 |
| `agents/` | 五个文本角色和行业规则。执行以这里的现行规则为准 |
| `schemas/` | 分镜、素材清单和编目的字段契约 |
| `config/` | 不含密钥的配置。真实密钥只放在环境变量或被忽略的本地文件里 |
| `docs/modules/product-material-pipeline-v1/` | 模块说明、验收规范和实现记录 |
| `material-library/` | 给下游剪辑的目录格式。具体产品卡和成片记录留在本机 |
| `output/` | 本机上的生成图，按商品分目录，保留版本 |
| `runtime/` | 进度和变更记录可以在仓库里。某次出图的提示词、参考图绑定和人设复述留在本机 |
| `tests/` | 门禁和契约测试 |
| `imports/` | 带进来的参考规则和来源说明 |
| `vendor/` | 本机部署的第三方程序，不在公开仓库里 |

五个文本角色是：`creator` 写分镜，`reviewer` 审方案并改图像提示词，`motion` 写图生视频动作，`pace` 改成片节奏，`enricher` 回填静帧能力字段。默认配置在 `config/doubao_text.json`。

## 本地运行

在仓库根目录执行。Python 调用前先看 `config/env.example`，把需要的变量放进环境，不要写进会提交的文件。

```text
python scripts/material-flow.py policy --case cases/<product_id>/case.json
python scripts/material-flow.py create --case cases/<product_id>/case.json --run <run-id>
python scripts/material-flow.py summarize --run <run-id>
python scripts/material-flow.py review --run <run-id>
python scripts/material-flow.py score-template --run <run-id>
python scripts/material-flow.py score-submit --run <run-id> --by <operator>
python scripts/material-flow.py gate --run <run-id>
python scripts/material-flow.py jobs --run <run-id> --shots <shot-id,shot-id>
```

`--shots` 必须是已经提交的打分表里选中的镜头。视频侧使用 `video-jobs`、`visual-review-template`、`video-submit`、`video-poll`，参数以脚本里的说明为准。付费调用要先有一份写明次数上限、有效期和同意范围的人工授权，再记一笔账，然后才发请求。没有授权、超过上限，或接口返回含糊，都停止，不自动重试。

视频供应商是分开的：

- 官方视频接口可以带参考视频，契约在 `config/minimax_official.json`。
- 另一路只接受提示词、时长和参考图，不接受参考视频，契约在 `config/autodl_h3_z0902.json`。这路默认关闭网络和生成，只做演练。两条路由不能混用，工作流对不上就拒绝。

## 公开仓库里有什么

可以放进这个仓库的，是流水线规则、脚本、测试、字段契约、不含密钥的配置模板，以及角色和行业规则的现行文本。素材库只保留目录格式说明。

禁止放进这个仓库的，是产品图、参考图、生成图、视频、音频、封面、出镜人的外貌和人设、\cases/\ 里的商品与人物资料、某次生成的提示词和供应商回执、密钥、第三方程序、缓存、虚拟环境和模型权重。这些留在运行机器上，不因为不上传就删除。

克隆之后可以看到流程和契约，看不到具体商品的图片和人物资料。

## 提交修改

直接推送到这个仓库需要仓库主人按 GitHub 用户名单独授权。阅读和提议修改不需要授权：克隆仓库，在自己的分支上改，然后开 Pull Request。

改动如果碰到生成、审核或入库，请说明它影响哪一个门禁，并带上对应测试或一份静态核对结果。不要把密钥、生成图和视频加进提交。
