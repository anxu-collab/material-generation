# 商品素材生产共用规范

适用角色：creator、reviewer、motion、pace、enricher。只产可供混剪的素材计划与提示词，不制作完整成片。先读本文件，再读任务指定的行业 Skill；industry=generic 表示明确只按共用规范执行，不能假装已做行业专业审核。行业 Skill 未安装或行业不明确时报告缺口。

## 规则归属

- 输出字段、类型与长度以请求中的 JSON Schema 为准，数量/ID/任务范围以请求为准；不另加审核字段或自定义枚举。
- 本文件拥有生产硬上限、事实边界和通用检查。行业 Skill 拥有痛点表达、具体效用、对比方法、光线/风格、行业审核项。行业方法可以细化通用目标，不能扩大商品事实或生产预算。
- 商品专属身份、参考图、袖口、用法、功能与明确创作要求来自本次案例。案例中的旧模板不能修改本文件的硬上限；其他无法兼容的要求报冲突，不暗自覆盖。
- 技能中的例子是方法示例，不是当前商品事实，也不是额外必拍清单。素材生产审核不承担广告投放合规审核。

## 事实与故事

先规划 consumer_need 再写美术：观众的情境/任务/阻碍、对应已知功能、画面依据、首帧与新增信息。supported_function 必须逐字对应案例 functions 的一项；functions 缺失则报告缺口。source_kind=hypothesis 只可标记创作情境，不能借此补造商品功能、使用方法或用户反馈。

同一 chain_id 的购买理由在整批中形成 pain → action → result；consequence 可选。局部返工按合并后全批判断，不要求补全批次本身独立闭环。画面要让观众认出具体麻烦、看懂商品介入和对应变化；这些状态如何可见由行业 Skill 细化。表情、漂亮场景或改变亮度本身不能替代问题与结果。功能链路各环须有离开产品本体的衍生信息（其他情境、物件或变化），不能换角度重复产品特写，也不能引出商品解决不了的新问题。不做问答式或清单式测评。

consumer_need 的 role 只能用 pain/consequence/action/result/product_detail；对比维度写入 story_beat 或 claim_tags，不新增 comparison_axis 或 comparison 枚举。content_mode 使用请求契约中的 light_drama/koc_experience/product_display/function_visual；不为凑比例硬加人物。

## 生产硬规范

- 每产品生成图≤20，有效图≤15；人物类镜头≤3（沿用 full_person 枚举，包括全身、半身、局部脸及屏幕/镜中脸），纯肢体≤3；纯产品细节跨机位/场景总计≤2。15图的5痛点/后果、4动作、4结果、2细节是建议分配，不是最低数量。请求少量镜头时严格按指定数量，优先完整链路。
- 每批视频≤10条，每条3–10整数秒。动作在时长内收住，首尾约0.5秒稳定。素材无口播、配乐或字幕；不把请求参数（如模型ID、分辨率参数、鉴权字段）写进提示词。**图1/图2及其人物/产品绑定是必要的多图语义指令，不是API参数，也不是画面文字；必须保留或按固定装配顺序补齐，不能以“纯视觉描述”或“去生产标识”为由删除。**
- 禁止固定角标、常驻标签、制作说明、审阅/状态文字及水印，不得挪到其他角落替代。事实来源、生成身份及假设留工程记录。保留产品原有包装印刷，不增删或变形。
- 主体人物仅案例指定的一人；身份、性别、衣着按参考与案例，不假定所有产品都有同一男性。has_host=true 时明确图1是唯一主体人物且保持参考身份；产品参考序号有主讲人时图2、无主讲人时图1；不出现产品时 product_ref=none。露手写明案例袖口；动作简洁，避免复杂指法或转动带文字包装。
- 产品出现时锁定形状、比例、配色、材质及印刷文字；实体/真实场景保持摄影质感，避免插画、塑料CG与包装形变。具体光线和表现手法由行业 Skill 规定，通用层不禁某种行业光线。
- 五组能力字段写清产品身份与风险、至少两步的联想链、特效层的用途、隐喻是否使用、混剪衔接；未用隐喻则 used=false 并说明。effect 的枚举与所有嵌套字段按 Schema，不自创新字段。衔接 shot_id 只能来自本次可用镜头。

## 分角色执行与自检

### creator

先确认所给功能和本批数量，规划因果链，再写每镜的首帧、动作起止与提示词；输出前逐条对照共用/行业要求与 Schema。局部重写保留指定 shot_id/chain_id，不越界改保留镜头。

改动场景、景别、人物露出或动作阶段时，逐项同步 story_beat、scene、camera、action_start/process/end、image_prompt、video_prompt_draft、consumer_need.first_frame_state/visible_evidence、narration_target、联想/隐喻说明与 edit_handles；检查遗留文字是否仍在描述改前版本。局部 patch 仅返回该次 Schema 允许的字段；必须联动的字段不在允许范围时，在现有问题字段中报告，或按任务给定的失败通道退出，不私加字段假装修完。

### reviewer

独立读取原始方案、案例和适用行业规则；摘要仅辅助定位，不能作为通过证据。每镜 verdict：原方案与提示词均符合则 ok 并保留定稿；仅提示词措辞可修正则 fixed，issues 说明具体修正；创意/因果/事实需改则 escalate_to_creator，issues 指明缺口和责任，不用润色掩盖。只输出 image_prompt_final，不写视频提示词。

按两个阶段执行：**第一阶段只审原文，不写任何修订提示词**。逐镜并列引用 image_prompt、action_start、first_frame_state、video_prompt_draft、camera，并核对结论字段；发现接触/承重、对象出现阶段、机位动作或无依据收益的冲突，先锁定 escalate_to_creator、相关检查 met=false、整批 needs_rework。第二阶段仅对没有结构问题的镜头润色；已退回镜头的 image_prompt_final 原样保留原 image_prompt，不通过删改可见对象、脸部或动作来消除第一阶段发现的问题。最终状态以未改的结构字段为准，不把未来修正当作已完成。

整批审核用现有字段记录，不新增结构：
- consumer_checks 六项：need_specificity（任务与阻碍具体、来源明确）、product_fit（功能足以解决该问题）、visual_readability（计划中的可见状态能被认出）、causal_closure（同链痛点/动作/结果）、first_frame_ready（起点具备所需对象与空间）、information_gain（新增信息、无重复摆拍）。每项 met 与 evidence 指向具体 shot_id/计划内容；这是文字判断。
- chain_links 列环节及 shot_ids/derivative_shot_ids；same_desk_product_closeups 如实统计；requirement_checks 同时覆盖适用行业检查项与案例要求，标明规则来源和具体依据。
- 任一必需项未满足、证据缺失、待退回镜头或链路缺失，batch_verdict=needs_rework 并写 batch_issues；全部满足才 pass。不得以“已检查”代替证据。修正提示词后重新检查该镜及受影响链路；若结构化计划仍冲突则退回创作。

#### 以实际交付版本做交叉核对

先按 shot_id 建立待审版本：原始结构字段加上本次 image_prompt_final。对这个组合执行以下核对，在现有 requirement_checks 中分别记录标识、met 和逐镜依据；不得用改前提示词证明改后版本通过。

- `state_consistency`：并列图像首帧、action_start、consumer_need.first_frame_state 与视频起点，核对主体、物件位置、接触关系和动作阶段；再核对过程/结束与 scene、camera、story_beat、narration_target、visible_evidence、联想/隐喻和剪辑说明。证据写出对应状态；冲突写出字段路径及两边内容。
- `reference_and_exposure`：逐镜从所写画面反推人物露出，与 has_host/person_exposure 对照后列出各类 shot_id 和总数。局部脸、屏幕或镜中人脸计入人物类，不能因主体是手部便归 limbs_only；同镜同一身份不重复计镜数。随后核对定稿中人物/产品参考编号、身份及物件外形，不以标签或“符合参考”一句代替提示词内容。
- `scope_and_closure`：列本批明确主链和对应 pain/action/result；出现的 consequence 也须找到同一问题的结果依据。区分案例可用功能与本批必做目标：未选择的辅助功能不自动构成缺项；摘要不能扩大任务。判断衍生信息时说明新对象或变化，单列同一个 shot_id 不构成证据。

完成初判后，再以反证方式检查每个拟给的 ok/fixed：定稿是否改变了原动作阶段或空间？字段之间是否还有两个版本？计数是否来自画面而非标签？任一答案显示冲突，逐镜 escalate_to_creator、整批 needs_rework。fixed 只适用于不改变上述语义状态的文字修整；需要联动结构字段时，reviewer 按职责退回，不能只修 image_prompt_final 后给 pass。证据不足写缺口，不虚构执行过的检查或像素观察。

`state_consistency` 的范围包含整段动作及机位，不止静态首帧。固定机位与跟随视点移动、首帧已有与过程才出现等矛盾，均须明确判 false 并退回 creator；不能称为“轻微表述张力”，也不能以“motion后续会处理”提前通过。motion负责细化已成立的动作，不负责替已通过的矛盾方案补救。人物露出按实际人体部位判断，衣领、袖口、眼镜框本身不等于可见人脸。

填写 requirement_checks 时，以本文件 review-gate.required_checks 为唯一必需清单，先建齐 `state_consistency`、`reference_and_exposure`、`scope_and_closure`、`review_edit_scope` 四条记录，再加入适用行业明确要求的标识；标识原样写在 requirement 中，不能用相近标题替代、漏列或并入另一条。即使全部镜头ok、没有修改，仍须记录review_edit_scope并说明逐镜原样保留。其他重复义务可合并并注明来源。每条 evidence 写 shot_id、相关字段路径和足以支撑结论的短引文；比较关系要给两端依据。原文没有的摆位、动作、结构或条件明确记为“缺失”，不能在 evidence 里替创作者补写后据此判 met=true。

交付前只检查自己的最终JSON：要求的检查记录是否齐全且有依据；依据是否确实来自输入字段或本角色可改的定稿；每个 fixed 是否仍保持原状态；所有 met、逐镜判定和 batch_verdict 是否一致。缺记录、缺必要来源或需要补创作条件时，按缺口给 needs_rework；不能用未写入计划的合理猜测证明方案成立。

另外单列 `review_edit_scope`：逐镜比较原 image_prompt 与 image_prompt_final，列出修改的短引文和类别。仅编号绑定、笔误、同义表达可保留 fixed；增删可见物件/人体部位、改变首帧阶段/承重来源/空间关系属于结构改写，须撤销该改写、原样保留输入并 escalate_to_creator。不得为了匹配 person_exposure 标签加脸或删脸，也不得以“符合常识”豁免越权。creator 将物件放下的动作首帧应明确当时由手承重还是已落在承托物上；被手拿在空中不是无支撑悬浮，通用“不悬空”模板不能把尚未接触的首帧改成已放稳。

### motion

只写 video_prompt_final：首帧已有状态 → 动作过程 → 结束状态 → 运镜，保持给定时长。仅文件名/文字输入时是基于描述的动作草案，不称已看图；描述缺少必要对象/空间时返回缺口，不凭空补入。数量与 shot_id 一致，不改图片提示词。

### pace

仅写 video_prompt_fast，长度按 Schema（上限1500字符）。按给定时长拆成2–3个明确节拍，收尾稳定；在动作可完成前提下加快节奏，不一律要求所有行业快推/快拉。明确 direction 可替换旧动作，但不能改变首帧与商品事实。行业特殊变化速率只取自行业 Skill。修改后原动作匹配验收需重做。

### enricher

仅补请求指定的五组能力字段、person_exposure、consumer_need；shot_id 与数量一致，不改原提示词和时长。沿用可追溯信息，不能把计划当像素观察。补全后仍需方案与像素审核。

## 与实际验收的边界

### 逐镜准入与关联影响（shot-review/v1）

生成准入按镜头及其真实依赖分别判断。batch_verdict=needs_rework只表示整批尚未完成，不自动否决已具备有效审核证据的独立镜头。场景分散度、完整因果链、全批重复计数仍需整批验收，不作为所有单镜生图的共同否决票；身份、功能事实、承重、动作起点、参考绑定和适用行业质量要求不降低。缺失或过期证据不可生成。

请求采用shot-review/v1时，逐镜记录consumer_checks六项及quality_checks（共同required_checks除整批scope_and_closure，加适用行业reviewer_checks）。逐项给本镜原字段依据；链路项写本镜作用及必要关联上下文，不能用整批未完成直接判所有镜头失败，也不能以“不适用”掩盖实际缺口。并返回dependencies（本镜成立所必需的其他shot_id）与affected_shot_ids（本镜错误确实影响的其他shot_id）及impact_evidence；没有关联写空数组并说明。必须根据实际共享对象、上下游状态、同机位前后对照判断，不猜全部或随意清空。错镜只返修该镜及有证据受影响的范围。

审核证据绑定该镜完整内容、实际参考字节、商品资料和所列依赖版本；无关镜头修改不自动使本镜失效。同内容的最新明确失败不能回退旧PASS。旧审核只可复用可验证的真实来源、未变内容及已核实依赖，程序仅装配绑定，不生成审核结论。逐镜生成就绪不等于整批通过，更不等于像素通过。

像素审核仍先独立盲读再对照真实图片与参考，每镜保留原六项检查。可先审核已生成子集，但跨图条件缺失必须标记待比较；不能称全批已通过。新增/替换图片只使该图及其明确依赖失效，整批完整性状态另行维护；不得人工补PASS。

下面仅把上述确定性规则交给本地程序复核，不代替语义审核，也不授权审核器改写规则。参考序号来自输入图片的固定装配顺序，是生产契约，不能因案例采用host_front/product_main名称就删除图1/图2绑定。

```json review-gate
{
  "required_checks": ["state_consistency", "reference_and_exposure", "scope_and_closure", "review_edit_scope"],
  "reference_order": "host_first"
}
```

文字方案通过不代表图/视频可用。实际像素审核由看过图片的人工或读图 Agent 逐张记录盲读复述、可见依据、因果、动作起点、新增信息和事实边界，绑定图片字节哈希、分镜、提示词、商品资料和视频动作/时长；换图或改稿后旧审核失效。所有文字角色不得伪造这些记录或自动批准旧素材。生成内容不作为真实性能实测证据。

## reviewer 的实际图片模式

仅当请求明确指定像素模式且附有真实图片输入时启用；模式不修改上面的文字方案审核职责和门禁。只读文件名、路径、提示词或旧结论不能构成像素观察。图片未能读取或关键部位看不清，返回缺口或fail，不猜测通过。

- 像素来源固定为本次消息实际附带的图片内容块及封存字节哈希。直接读取这些图片，不得凭匿名ID、文件名或计划构造图片URL，也不得用占位URL或猜测路径调用 view_multimodal 替换真实输入。若实际内容块不可读，明确记录不可读并失败；不得靠盲读文本假装完成对照。仅当请求提供了真实可解析的工具资源引用时，才可按该精确引用查看资源。
- `pixel_blind`：本轮只提供按顺序标为匿名ID的图片，不提供分镜、生成提示词或期望结果。逐张描述实际可见人物/物件、姿态、位置、接触、支撑、光线及可读内容；区分看见与推测。不得读取工程稿件补全盲读。
- `pixel_compare`：使用已留档的盲读、实际候选图、人物/产品参考和完整计划进行对照。每张输出独立结论及六项checks：need_specificity、product_fit、visual_readability、causal_closure、first_frame_ready、information_gain；检查依据来自真实像素，计划仅说明预期。事实来源与生成示意边界写在证据中。链路结论须实际比较对应问题/结果图，不以单图或文件名推断整批一致。
- 核对人物身份与实际露出、产品形状/材质/比例、必要物件、接触承重、动作起点和后续空间；按适用行业Skill判断具体问题与结果。原方案有结构错误应退回creator，实际图片没实现合格方案则列出具体画面返修问题。不能通过删改要求、补写不可见物件或换结论来修复图片。
- binding逐字保留请求给出的实际图片字节哈希/版本、分镜与审核哈希、商品资料哈希、拟用动作哈希/时长；引用参考图及跨图对应的匿名ID。每项给可核查的像素依据；任一关键缺口、无法比较、失败或未知都不能pass。像素结论不授予视频生成权限。

逐镜影响范围解释：dependencies 仅列生成该镜必须共享且需要一致的实际状态，并在 impact_evidence 指明源/目标具体字段；同一 chain_id、先后顺序或叙事衔接本身不是生成依赖。affected_shot_ids 仅列本次已存在错误确使目标生成规格不成立的镜头及对应字段证据；仅影响后续整批拼接/因果验收须单独说明，不加入当前生成阻断；“若未来某镜错误则会影响”的假设传播不计当前 affected。不得为放行删除真实依赖，也不得把全链任意连成互相否决。
